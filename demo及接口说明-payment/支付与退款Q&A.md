# 支付与退款 Q&A

> 本文档汇总 DS_Course 系统中**支付下单**与**退款**相关的全部业务场景（正常 + 异常），以及后端对应的处理逻辑和设计决策原因。
> 最后更新：2026-06-09

---

## 一、支付下单场景

### Q1. 系统支持哪些下单方式？

| 方式 | 接口 | 适用场景 | 状态流转 |
|------|------|----------|----------|
| 小程序支付 | `payCreate` | 学员在微信小程序内自助购买 | `pending_payment` → 支付回调 → `paid` → 审核 → `verified` |
| 线下订单 | `payOrderCreateOffline` | 业务员代客录入（银行转账/现金等） | `paid`（创建即视为已收款）→ 审核 → `verified` |

**设计原因**：
- 线下订单不需要走微信支付，业务员已确认收到款项，所以创建时直接置为 `paid`。
- 小程序订单需要等微信支付回调确认后，才改为 `paid`，防止虚假支付。

---

### Q2. 线下订单创建时，为什么必须传 `created_by_staff_id`？

**处理逻辑**：
```cpp
if (created_by_staff_id <= 0)
{
    return 400; // "Offline orders must provide created_by_staff_id"
}
```

**设计原因**：
- 线下订单是业务员录入的，必须留痕，便于后续业绩统计、责任追溯和审核。
- 小程序订单的 `created_by_staff_id` 为 0，表示用户自助下单。

---

### Q3. 订单金额和名额可以为 0 吗？

| 字段 | 小程序订单 | 线下订单 | 说明 |
|------|-----------|---------|------|
| `amount`（金额） | 必须 ≥ 0 | 必须 ≥ 0 | `amount=0` 表示免费赠送名额 |
| `slot_quantity`（名额） | 必须 > 0 | 必须 > 0 | 不允许为 0 或负数 |

**处理逻辑**：
```cpp
if (slot_quantity <= 0) return 400; // "slot_quantity must be greater than 0"
```

**设计原因**：
- `slot_quantity=0` 会导致订单无实际意义（充了个寂寞），且后续退款计算会出现负数（`order_refundable_slots = 0 - consumed - refunded`）。
- `amount=0, slot_quantity>0` 是**合法场景**：业务员给客户免费赠送课程名额。

---

### Q4. 订单的 `unit_price` 是怎么计算的？

**处理逻辑**：
```cpp
int unit_price = (slot_quantity > 0) ? total_amount / slot_quantity : total_amount;
```

**设计原因**：
- 单价由前端传入的 `amount / slot_quantity` 计算，后端**不做单价校验**。
- 业务上允许同课程不同订单的单价不同（如促销价、老学员价），所以不做统一校验。
- `slot_quantity=0` 时防除零，但此时前面已拦截，不会走到这里。

---

### Q5. 线下订单为什么需要审核？

**状态流转**：
```
创建 → paid（已收款） → pending_review（待审核） → verified（已核销）/ rejected（拒绝）
```

**处理逻辑**：
- 线下订单创建后 `verification_status = "pending_review"`，课程账户**不会立即生效**。
- 财务/管理员调用 `payOrderReview` 审核通过后：
  - `verification_status = "manual_verified"`
  - 课程账户 `total_slots += slot_quantity`, `total_recharge_amount += amount`
  - 写入流水 `type = order_recharge`

**设计原因**：
- 线下支付方式多样（银行转账、现金、支付宝等），需要人工确认款项到账和凭证真实性。
- 小程序支付通过微信官方通道，支付回调即视为到账，自动 `verified`。

---

### Q6. 已支付/已审核的订单还能修改吗？

| 订单状态 | 能否修改 | 能否删除 |
|----------|---------|---------|
| `pending_payment`（待支付） | ✅ 可修改 | ✅ 可删除 |
| `pending_review`（待审核） | ❌ 不可修改核心字段 | ✅ 可删除 |
| `rejected`（审核拒绝） | ✅ 可修改 | ✅ 可删除 |
| `paid`/`verified` | ❌ 不可修改 | ❌ 不可删除 |
| `refunding`/`refunded` | ❌ 不可修改 | ❌ 不可删除 |
| 已软删除（`deleted_at` 不为空） | ❌ 不可修改 | ❌ 不可重复删除 |

**设计原因**：
- 已支付/已审核的订单涉及资金流动和课程账户变更，允许修改会导致账目混乱。
- 拒绝的订单说明审核未通过，允许修改后重新提交。
- 软删除保留审计追溯能力，不真正删除数据。

---

### Q7. 订单超时未支付怎么办？

**处理逻辑**：
- 后台定时任务扫描 `status='pending_payment'` 且超时的订单。
- 调用 Go 支付服务查单 API 补偿状态。
- 确认未支付后，原子 `UPDATE + WHERE status='pending_payment'` 关闭订单，防止与回调竞态。

**设计原因**：
- 微信回调可能丢失或延迟，需要兜底机制确保订单状态最终一致。
- 原子更新保证：如果回调和定时任务同时执行，只有一个能成功修改状态。

## 二、退款场景

### Q8. 退款申请的基本校验有哪些？

**6 条校验规则**：

1. **订单存在且未软删除**
2. **订单状态为 `paid` / `verified` / `refunding`** — 未支付/已关闭的订单不能退款
3. **退款金额 ≤ 订单总金额**
4. **累计退款（已完成 + 本次）≤ 订单总金额**
5. **同一订单有 `pending`/`approved` 退款不可重复申请** — 防止并发重复退款
6. **5 分钟内同一订单同一申请人仅允许一笔 `pending` 退款** — 防刷

**设计原因**：
- 前 3 条是基本业务规则，防止退不存在的钱。
- 第 4 条防止超额退款。
- 第 5、6 条是并发安全 + 防重复提交机制。

---

### Q9. 退款时 `amount` 和 `refund_slot_quantity` 的关系是什么？

**核心规则**：

```
amount 和 refund_slot_quantity 不能同时为 0
```

| 场景 | amount | refund_slot_quantity | 是否允许 | 说明 |
|------|--------|---------------------|---------|------|
| 正常退款 | > 0 | > 0 | ✅ | 同时退金额和名额 |
| 只退金额 | > 0 | = 0 | ✅ | 名额不退，只退钱 |
| 只退名额 | = 0 | > 0 | ✅ | 钱不退，只收回名额 |
| 两者都为 0 | = 0 | = 0 | ❌ | 无意义请求 |

**设计原因**：
- 现实中存在"名额已用完但还有钱可退"（只退金额）和"钱已退完但名额没退完"（只退名额）的情况。
- 同时支持两者为 0 会创建无意义的退款单，所以拒绝。

---

### Q10. 退款名额的校验逻辑是怎样的？

**处理逻辑**：

```cpp
// 1. 账户级：该学员该课程的可用名额
int refundable_slots = acc.total_slots - acc.consumed_slots - acc.refunded_slots;

// 2. 订单级：该订单原始名额 - 该订单已消耗 - 该订单已退
int order_refundable_slots = ord.slot_quantity - order_consumed_slots - order_refunded_slots;

// 3. 取两者较小值
int max_refund_slots = std::min(refundable_slots, order_refundable_slots);
```

**自动截断**：
- 如果 `refund_slot_quantity > max_refund_slots`，自动截断为 `max_refund_slots`。
- 如果 `max_refund_slots <= 0` 且请求退名额，返回 400。

**设计原因**：
- **账户级校验**：防止退超过学员实际拥有的名额（包括其他订单充值的）。
- **订单级校验**：防止退超过该订单购买的名额，尤其是防止把别人转赠来的名额一起退掉。
- **自动截断**：容错设计，前端传多了不会直接报错，而是退最大可退数量。

---

### Q11. 为什么已消耗的名额不影响纯金额退款？

**处理逻辑**：
- 当 `refund_slot_quantity = 0`（只退金额）时：
  - 不执行名额相关校验和截断。
  - 只校验 `refund_amount + refunded_total <= ord.total_amount`。

**设计原因**：
- 报名消耗名额不消耗金额，金额和名额是独立的两套账目。
- **类比电商"退款不退货"**：如淘宝等平台，商品已签收甚至已使用，依然支持全额退款（仅退金额，商品无需退回）。课程场景中名额已消耗等价于"货已用"，退金额是合理诉求。
- **课程退课场景**：学员已上课/已报名（名额已消耗），但因课程质量、个人原因等要求退课退费时，只需退金额即可，课程账户中的名额状态已不重要，无需强制扣减名额才能退款。
- 是否允许"名额已用完但全额退款"由**业务规则**决定，代码不做一刀切。
- 财务审核环节 (`payRefundReview`) 由人工把关，审核人员可以看到订单历史和账户余额，有能力判断合理性。

---

### Q12. 退款审核通过后会做什么？

**处理流程**：

1. **更新退款单状态** → `completed`
2. **更新订单状态**：
   - 累计退款 ≥ 订单总额 → `refunded`
   - 否则 → `refunding`
   - 清空 `verification_status`
3. **更新课程账户**（如果是课程订单）：
   - `refunded_slots += refund_slot_quantity`
   - `refunded_amount += refund_amount`
   - 带乐观锁：`WHERE (total_slots - consumed_slots - refunded_slots) >= refund_slot_quantity`
4. **写入流水**：`type = "refund_deduct"`, `slots_change = -refund_slot_quantity`, `amount_change = -refund_amount`

**设计原因**：
- 退款分两个阶段（申请 → 审核）是为了让财务有机会复核，防止误操作或恶意退款。
- 乐观锁防止并发退款导致超额退名额。
- 流水记录保证账目可追溯。

---

### Q13. 退款审核时，课程账户可用名额不足怎么办？

**处理逻辑**：
```cpp
if (acc_affected == 0)
{
    conn->rollback();  // 回滚退款状态更新
    return 400; // "退款失败：课程账户可用名额不足"
}
```

**设计原因**：
- 乐观锁拦截并发冲突（如两笔退款同时审核，或退款和报名同时进行）。
- 回滚保证：退款单状态不变，订单状态不变，课程账户不变，三者保持一致。
- 财务可以稍后重新审核。

---

### Q14. 部分退款后订单还能继续退吗？

**可以**，只要满足：
- 累计退款金额 < 订单总金额
- 累计退款名额 < 订单原始名额（订单级）
- 课程账户还有可用名额（账户级，仅退名额时检查）
- 没有 pending/approved 的退款单在途

**设计原因**：
- 支持多笔部分退款，适应灵活的业务场景（如先退 1 个名额，后续再退 1 个）。

## 三、课程账户与退款的关系

### Q15. 课程账户的可用名额怎么计算？

```
available_slots = total_slots - consumed_slots - refunded_slots
```

| 字段 | 含义 |
|------|------|
| `total_slots` | 累计充值/获得的名额总数 |
| `consumed_slots` | 累计报名消耗的名额 |
| `refunded_slots` | 累计退款扣减的名额 |

**注意**：`refunded_amount` 是独立的金额账目，不影响名额计算。

---

### Q16. 报名消耗名额后退款金额会受影响吗？

**不会**。报名只扣减 `consumed_slots`，不扣减 `total_amount` 或 `refunded_amount`。

**举例**：
- 用户购买 4 个名额，金额 ¥4000
- 报名消耗 4 个名额
- 申请退款：
  - `amount=4000, refund_slot_quantity=0` → ✅ 只退金额，名额不退
  - `amount=0, refund_slot_quantity=4` → ❌ 可用名额为 0，无法退名额

**设计原因**：
- 金额和名额是独立维度。名额用完了不代表钱不能退（如课程质量问题）。
- 是否允许退钱由财务审核把关。

## 四、异常场景汇总

| 异常场景 | 接口 | 返回码 | 处理方式 |
|----------|------|--------|----------|
| `slot_quantity <= 0` | 创建订单 | 400 | 直接拒绝 |
| `amount=0 && refund_slot_quantity=0` | 退款申请 | 400 | 直接拒绝 |
| 退款金额 > 订单剩余金额 | 退款申请 | 400 | 直接拒绝 |
| 退款名额 > 可用名额 | 退款申请 | 自动截断 | 截断为最大可退 |
| 可用名额=0 但请求退名额 | 退款申请 | 400 | 拒绝 |
| 订单有 pending/approved 退款 | 退款申请 | 400 | 拒绝重复申请 |
| 5 分钟内同一订单重复退款 | 退款申请 | 400 | 拒绝 |
| 课程账户乐观锁失败 | 退款审核 | 400 | 回滚，提示名额不足 |
| 已退款订单修改/删除 | 订单修改 | 400 | 拒绝 |
| 已删除订单审核/退款 | 订单操作 | 400 | 拒绝 |
| 缺少 `created_by_staff_id` | 线下订单创建 | 400 | 拒绝 |
| 支付回调重试 | 支付回调 | 200 | 幂等：已 paid 直接返回成功 |

## 五、设计原则总结

1. **金额与名额解耦**：金额和名额是独立维度，退款时允许只退其一。
2. **两阶段退款**：申请 → 审核，给财务复核机会。
3. **自动截断而非报错**：退款名额超限时自动截断到最大可退，提升容错性。
4. **乐观锁防并发**：所有涉及状态变更的写操作使用原子条件更新。
5. **幂等设计**：支付回调、重复退款申请都有幂等保护。
6. **审计留痕**：操作日志、课程账户流水、退款记录全链路可追溯。
7. **人工兜底**：复杂业务判断（如名额已用完是否退钱）交给财务审核，代码不做过度拦截。
